---
title: "Usage by Properties"
description: "Group and filter a customer's usage and cost by event properties such as region, model or instance, through the portal analytics API"
---

A usage chart that only splits by feature cannot answer the questions customers actually ask: which region is driving the bill, which model costs the most, which instance spiked last week. With usage properties turned on, the portal analytics API groups and filters a customer's usage and cost by the properties on your events, so a portal front end you build can answer them.

The feature is off by default. You turn it on per environment and choose which properties customers can see.

<Note>
**The hosted portal has no property controls**

The hosted Customer Portal doesn't group or filter by event property, and turning on usage properties adds no toolbar to it. The setting applies to the portal analytics endpoints, for a portal front end you build on the API.
</Note>

## Building property controls

A portal front end can offer three controls on these endpoints. The example below groups usage by `cloud_provider` with an `env` filter.

| Control | What it does | Request field |
| ------- | ------------ | ------------- |
| **Features** | Narrows the view to one or more features. Useful when the customer has usage on two or more features | `feature_ids` |
| **Group by** | Splits the chart and the breakdown table by one property, for example `region` | `group_by` |
| **Filter** | Keeps only usage whose property matches the chosen values, for example `cloud_provider` is `aws`. The values endpoint takes a `prefix` for search | `property_filters` |

To drill down, combine the two: filter `region` to `us-east-1` and group by `instance_id`. In the example, active filters appear as removable chips under the toolbar, with **Clear all**.

<Frame>![Example property toolbar: usage grouped by cloud_provider with an env filter, showing cost per provider in the chart and the breakdown table](/images/docs/customers/customer-portal/usage-properties-toolbar.png)</Frame>

When usage is grouped in the example:

- **The chart shows cost per property value.** Cost adds up across features, where usage in different units does not.
- **The top 8 values get their own line.** The rest are combined into **Other**.
- **Usage without the property** appears as **(none)**.
- **The breakdown table** lists one row per value, sorted by cost.
- **Metric cards** (total spend, cost, margin) respect the active filters.

## Turning it on

The dashboard has no control for usage properties. Turn them on through the settings API by writing `analytics_config` into the `customer_portal_config` setting. This changes what the portal analytics endpoints accept, not what the hosted portal shows:

```bash
curl --request PUT \
  --url https://api.cloud.flexprice.io/v1/settings/customer_portal_config \
  --header 'x-api-key: <your_api_key>' \
  --header 'Content-Type: application/json' \
  --data '{
    "value": {
      "analytics_config": {
        "usage_properties": {
          "enabled": true,
          "allowed_keys": ["region", "model"],
          "hidden_keys": ["user_email"]
        }
      }
    }
  }'
```

| Field | Effect |
| ----- | ------ |
| `enabled` | Turns the feature on. It stays off until you set it to `true` |
| `allowed_keys` | Customers see only these properties. Leave empty to show all of them |
| `hidden_keys` | Customers never see these properties |

The write replaces `analytics_config` as a whole and leaves the rest of the setting, such as your sections and theme, as it is. Send all three fields every time, because a field you leave out is cleared.

Settings writes need a Super Admin user's API key. A service account key is refused. Saving the portal panel in the dashboard keeps this setting, but the panel's **Reset to defaults** deletes it.

To find property names for the lists, call `POST /v1/meter-usage/properties` with your API key. See [API](#api).

<Note>
**A property in both lists is hidden**

`hidden_keys` always wins over `allowed_keys`.
</Note>

## Which properties customers can use

A property is available to customers only when all of these hold:

- The feature is turned on, and the property passes your show and hide lists.
- **It is not an aggregation property.** Properties a meter aggregates on are always hidden: the `field` of a `SUM`, `MAX`, `AVG`, `LATEST` or `SUM_WITH_MULTIPLIER` meter, and any property used in a meter's `expression`. This applies across every meter on the same event. The fields of `COUNT` and `COUNT_UNIQUE` meters are identifiers, not quantities, so they stay available.
- **Its name uses only letters, numbers, `_` and `.`**

<Warning>
**Send property values as strings to group or filter by them**

Grouping and filtering read property values as strings. A property sent as a number, such as `"version": 2`, groups as if the property were missing and matches no filter. Send `"version": "2"` instead.
</Warning>

The properties endpoint builds its list from the customer's most recent usage of each meter in the requested date range. A property that only appears on older events may not be listed.

## API

A portal front end calls these endpoints with the customer's session token. Request bodies take `start_time`, `end_time` and optional `feature_ids`.

| Method | Path | Description |
| ------ | ---- | ----------- |
| `POST` | `/v1/customer/portal/analytics/properties` | Properties the customer can group and filter by, most used first |
| `POST` | `/v1/customer/portal/analytics/properties/values` | Values of one property, most used first. Takes `key`, an optional `prefix`, and `limit` (1 to 200, default 50) |
| `POST` | `/v1/customer/portal/analytics/revenue` | Accepts `group_by: ["properties.<key>"]` and `property_filters` |
| `POST` | `/v1/customer/portal/analytics/cost` | Accepts `property_filters` |

```bash
curl --request POST \
  --url https://api.cloud.flexprice.io/v1/customer/portal/analytics/revenue \
  --header 'X-Session-Token: <session_token>' \
  --header 'Content-Type: application/json' \
  --data '{
    "start_time": "2026-10-01T00:00:00Z",
    "end_time": "2026-10-31T00:00:00Z",
    "window_size": "DAY",
    "group_by": ["properties.region"],
    "property_filters": { "cloud_provider": ["aws"] },
    "expand": ["price"]
  }'
```

A property the customer cannot use returns `400` with `property key "<key>" is not available`.

The same lookups exist for your own API key at `/v1/meter-usage/properties` and `/v1/meter-usage/properties/values`. They take an `external_customer_id` and do not apply the show and hide lists, so you can see every property. Without `external_customer_id`, the properties lookup covers the whole environment.

## Limitations

- Grouping by a property with thousands of values returns every group, which makes the response large and slower to load.
- After you change the setting, open portal sessions can take up to a minute to reflect it.
