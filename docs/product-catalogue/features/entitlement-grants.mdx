---
title: "Entitlement Grants"
description: "Configure time-boxed usage quotas on entitlements: rolling windows, parallel limits, and amount-based caps with exhaustion alerts and overage billing"
---

A plain [entitlement](/docs/product-catalogue/features/linking-to-plans) resets once a billing period, which is the wrong shape for a product sold in bursts. An AI assistant that advertises "resets every 5 hours", or a plan that caps spend at $50 a day, cannot express that as a monthly limit. Entitlement grants turn an entitlement into a quota per window instead, on a clock of your choosing. Flexprice opens a window when usage starts, tracks consumption against the quota, fires a webhook when the quota is exhausted, and bills usage beyond it as overage on the invoice.

**Benefits:**

- **Rolling limits:** quotas measured in hours, days, or weeks instead of the billing period
- **Parallel limits:** stack independent windows on one feature, such as a 5-hour limit and a weekly limit
- **Amount-based quotas:** cap spend in currency, priced through your existing billing pipeline
- **Exhaustion webhooks:** `entitlement.grant.exhausted` fires when a window's quota is used up
- **Overage billing:** usage beyond the quota lands on the arrears invoice automatically

## Concepts

| Term | Meaning |
|------|---------|
| **Entitlement config** | An entitlement that carries a grant config (`grant_measure`, `grant_duration_unit`, and either `grant_quota` or `grant_unlimited`). Setting these fields is the opt-in; there is no separate type flag. |
| **Entitlement grant** | One concrete window instantiated from the config: a `valid_from`/`valid_to` range with an immutable quota and a usage snapshot. |
| **Measure** | What the quota counts: `quantity` (raw meter units) or `amount` (currency, priced through the billing pipeline). |
| **Aggregation mode** | How multiple grant configs on the same feature combine: `additive` merges quotas into one bucket, `parallel` keeps each config as its own independent bucket. |

## Configuring a Grant

Add the grant fields to a [create entitlement](/api-reference/entitlements/create-entitlement) or [update entitlement](/api-reference/entitlements/update-entitlement) request. The feature must be metered.

```bash cURL
curl -X POST "https://us.api.flexprice.io/v1/entitlements" \
  -H "x-api-key: <your-api-key>" \
  -H "Content-Type: application/json" \
  -d '{
    "feature_id": "feat_tokens",
    "feature_type": "metered",
    "entity_type": "plan",
    "entity_id": "plan_pro",
    "is_enabled": true,
    "grant_measure": "quantity",
    "grant_quota": "1000000",
    "grant_duration_value": 5,
    "grant_duration_unit": "hour",
    "grant_allocation_behavior": "first_usage",
    "aggregation_mode": "parallel"
  }'
```

### Grant Config Fields

| Field | Description |
|-------|-------------|
| `grant_measure` | `quantity` (meter units) or `amount` (currency) |
| `grant_quota` | Quota per window, as a decimal string. Omit it when `grant_unlimited` is set. |
| `grant_unlimited` | `true` for an allowance with no ceiling. Mutually exclusive with `grant_quota`, and only valid with `grant_duration_unit: subscription_period`. |
| `grant_duration_unit` | `hour`, `day`, `week`, or `subscription_period` |
| `grant_duration_value` | Window length, a positive integer. Not used with `subscription_period`, where the subscription cycle sets the length. |
| `grant_allocation_behavior` | `first_usage` (default) or `unit_start`. Controls where a window starts. Ignored for `subscription_period`. |
| `aggregation_mode` | `additive` (default) or `parallel` |

A fixed-duration window must be at least one hour long.

<Warning>
Grant configs are validated at write time:

- The feature must be metered. Meters with `MAX` aggregation or bucketed aggregation are not supported.
- All grant configs on one feature must share the same `grant_measure` and the same `aggregation_mode`. Additive configs must also share the same duration.
- `amount` grants require flat per-unit pricing on the meter. Tiered prices are rejected.
- An unlimited allowance needs `grant_duration_unit: subscription_period`. A recurring window needs a finite quota.
</Warning>

### Unlimited Allowances

Set `grant_unlimited: true` to give a customer an uncapped allowance for the billing cycle. The entitlement still reports usage and still appears in the ledger, but no quota is enforced, nothing is ever exhausted, and no overage is billed.

```json
{
  "grant_measure": "quantity",
  "grant_unlimited": true,
  "grant_duration_unit": "subscription_period",
  "aggregation_mode": "additive"
}
```

This is how you remove a ceiling from a metered entitlement. Use it in place of the legacy `usage_limit` and `usage_reset_period` fields, which metered entitlements are moving off.

### Where a Window Starts

`grant_allocation_behavior` decides how a new window is anchored:

- **`first_usage`** (default) starts the window at the timestamp of the usage event that opened it. An event at 2:07 opens a window that runs 2:07 to 7:07 for a 5-hour grant. Each customer's windows follow their own activity.
- **`unit_start`** rounds the start down to the boundary of the duration unit. That same event at 2:07 opens a window running 2:00 to 7:00. Use it when windows should line up with the clock rather than with the customer, such as an hourly quota that everyone sees reset on the hour.

The behavior applies only to fixed durations. A `subscription_period` grant always runs with the subscription cycle.

## How Grant Windows Work

Windows are usage-anchored. Flexprice does not open a window on a fixed schedule; it opens one when usage arrives:

1. The first usage event past the covered range opens a window, anchored according to `grant_allocation_behavior`.
2. The window runs for the configured duration: `valid_to = valid_from + duration`.
3. When the window ends, nothing happens until the next usage event. Idle periods open no windows, so an inactive customer accumulates nothing.
4. Windows never straddle billing cycles. A window that would end within an hour of the cycle boundary stretches to the boundary instead of leaving a short stub.

Each grant tracks two states in `grant_status`:

- `active`: usage is below the quota
- `exhausted`: usage reached the quota (`usage >= quota`)

Expiry is not a status. A grant is closed when `valid_to` has passed, regardless of how much quota was used.

### Grant Object

| Field | Description |
|-------|-------------|
| `id` | Grant identifier (`eg_` prefix) |
| `entitlement_config_id` | The entitlement this window was instantiated from |
| `customer_id`, `subscription_id` | Who the window belongs to |
| `scope_entity_type`, `scope_entity_id` | What the grant meters: `feature` and the feature ID |
| `measure` | `quantity` or `amount` |
| `quota` | The window's quota (immutable; the summed quota for additive groups) |
| `usage` | Usage consumed in this window, refreshed on each evaluation |
| `valid_from`, `valid_to` | The window boundaries |
| `grant_status` | `active` or `exhausted` |
| `quota_crossed_at` | When usage first reached the quota. Overage billing starts from this timestamp. |

## Reading Grant State

The exhaustion webhook tells you the moment a quota runs out. To ask what a customer's allowances look like right now, call [get customer usage summary](/api-reference/customers/get-customer-usage-summary).

```bash cURL
curl "https://us.api.flexprice.io/v1/customers/cust_01JXKA/usage" \
  -H "x-api-key: <your-api-key>"
```

Each grant-backed feature in the response carries its grant config and a `grant_state` holding the windows behind the numbers:

```json
{
  "features": [
    {
      "feature": { "id": "feat_tokens", "name": "Tokens", "type": "metered" },
      "current_usage": "120000",
      "total_limit": 100000,
      "is_unlimited": false,
      "grant_measure": "quantity",
      "grant_quota": "100000",
      "grant_duration_value": 1,
      "grant_duration_unit": "hour",
      "grant_state": {
        "allowances": [
          {
            "grant_id": "eg_01KYDEZ86JA78AM7F7Y2SMTRWE",
            "entitlement_id": "ent_01KYB5ESPNNB8DWFVQAFJN6KKZ",
            "measure": "quantity",
            "unlimited": false,
            "quota": "100000",
            "usage": "120000",
            "remaining": "0",
            "valid_from": "2026-07-25T14:00:00Z",
            "valid_to": "2026-07-25T15:00:00Z",
            "status": "exhausted",
            "is_active": true,
            "quota_crossed_at": "2026-07-25T14:42:11Z"
          }
        ]
      }
    }
  ]
}
```

### Allowance Fields

| Field | Description |
|-------|-------------|
| `quota`, `usage` | The window's ceiling and what has been spent against it |
| `remaining` | What is left. Absent on an unlimited window, where there is no ceiling to measure against. |
| `valid_from`, `valid_to` | The window boundaries |
| `status` | `active` or `exhausted` |
| `is_active` | Whether the window is open right now, decided by the server's clock. A window whose `valid_from` is still ahead reports `false`: it is scheduled, not closed. |
| `quota_crossed_at` | When usage first reached the quota. Absent while the window still has room, and on an unlimited window. Overage is billed from this timestamp, so this answers "when did it run out", which `valid_to` does not. |
| `unlimited` | `true` when the window has no ceiling |

<Note>
The response returns the most recent windows for the current billing period, capped at three per entitlement. An hourly allowance on a monthly cycle produces hundreds of windows, and a reader wants the live one and what led to it.
</Note>

For a **parallel** feature, the scalar figures cannot describe several independent budgets at once, so the response also carries a `buckets` array: one entry per budget, each with its own quota, cadence and measure. Read those instead of `total_limit` when `buckets` is present.

## Aggregation Modes

When a customer holds multiple grant configs on the same feature, such as a plan entitlement plus an addon entitlement, `aggregation_mode` decides how they combine.

### Additive

All configs merge into **one** window with `quota = sum of quotas`. Use this when an addon should top up the base allowance.

**Example**: The Pro plan grants 100K tokens per day. A booster addon grants another 50K per day. The customer gets one daily window with a 150K quota.

### Parallel

Each config opens its **own** independent window with its own duration. All windows meter the same usage stream. A request is within limits only while every applicable window has quota left; exhausting any one window puts the feature into overage for the remainder of that window.

**Example**: 1M tokens per 5 hours *and* 5M tokens per week, as two parallel configs. Heavy use exhausts the 5-hour window first; sustained use over days exhausts the weekly window even though no single 5-hour burst did.

## In the Dashboard

A customer's **Entitlements** table lists what they hold and how much of it they have spent:

| Column | Shows |
|---|---|
| Value | The allowance and its cadence, such as `100 / hour` or `300 / billing period`, or `Unlimited` |
| Mode | `Additive` or `Parallel` |
| Measure | `Quantity` or `Amount` |
| Usage | Consumption against the live allowance |

A parallel feature gets one row per budget, since no single pair of numbers describes them together.

Selecting a row opens **Grants**, the ledger of windows behind that number, with a start, an end, a status and the usage for each:

| Status | Meaning |
|---|---|
| Scheduled | The window has not started yet |
| Active | Open now, with quota left |
| Exhausted | Quota reached. Hover the pill for the moment it was crossed. |
| Closed | The window ended without the quota being reached |

## Use Cases

### Rolling Rate Limits for an AI Product

Cap token consumption in a rolling window that has nothing to do with the monthly invoice, the pattern used by AI assistants that advertise "resets every 5 hours".

```json
{
  "grant_measure": "quantity",
  "grant_quota": "1000000",
  "grant_duration_value": 5,
  "grant_duration_unit": "hour",
  "aggregation_mode": "parallel"
}
```

Add a second parallel config with `"grant_duration_unit": "week"` to layer a weekly ceiling on top of the burst limit.

### Daily Spend Cap

Cap what a customer's usage *costs* rather than how many units they consume. The `amount` measure prices usage through your existing meter prices, so a mid-window price change is respected.

```json
{
  "grant_measure": "amount",
  "grant_quota": "50",
  "grant_duration_value": 1,
  "grant_duration_unit": "day",
  "aggregation_mode": "additive"
}
```

The customer gets $50 of compute per day. Alert on exhaustion, or let usage continue and bill the excess as overage.

### Plan Plus Booster Addon

Sell top-ups without new plumbing. The plan carries a grant config; the addon carries another on the same feature with `additive` mode. Buying the addon raises the shared window's quota by the addon's amount. With `parallel` mode instead, the addon grants a separate window, useful when the addon's allowance runs on its own clock.

### Soft Limits With Billed Overage

Grants implement soft limits: usage is never blocked. When a window's quota is crossed, usage recorded after the crossing is billed as overage on the subscription's arrears invoice. Quantity overage is priced as billable units; amount overage lands directly as a charge. With parallel windows, overlapping overage periods are merged so a unit of usage is never billed twice.

<Note>
Overage folding skips line items with tiered prices, commitments, or true-up. Those price against the full cycle, so grant overage on them falls back to the standard billing calculation.
</Note>

## Exhaustion Alerts

Usage is measured shortly after events arrive, within roughly five minutes. When a window's usage reaches its quota the grant turns `exhausted` and a webhook fires, once per window. There is no recovery event: a fresh window with a fresh quota simply opens when the next one starts.

**Event type:** `entitlement.grant.exhausted`

```json
  "triggered_at": "2026-07-25T20:20:23Z",
  "subscription": {
    "id": "subs_01KYARKSC3GVX64QEF4T4ABS9X",
    "customer_id": "cust_01KYARB3TVZ0RZPDGC5P40NHHC",
    "plan_id": "plan_pro",
    "subscription_status": "active",
    "currency": "usd",

```

### Webhook Fields

| Field | Description |
|-------|-------------|
| `alert_type` | Always `entitlement_grant_exhausted` |
| `alert_status` | `in_alarm` when the quota is exhausted |
| `usage_ratio` | `usage / quota` at evaluation time, `1` or more when exhausted |
| `triggered_at` | When the exhaustion was detected |
| `subscription` | The owning subscription, without line items or plan expansions |
| `customer` | The customer the grant belongs to |
| `entitlement` | The entitlement config the window was instantiated from |
| `entitlement_grant` | The exhausted window, including `quota`, `usage`, and the window boundaries |
