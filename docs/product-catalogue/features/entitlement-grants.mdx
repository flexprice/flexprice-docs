title: "Entitlement Grants"
description: "Configure time-boxed usage quotas on entitlements: rolling windows, parallel limits, and amount-based caps with exhaustion alerts and overage billing"
---

A plain [entitlement](/docs/product-catalogue/features/linking-to-plans) resets once a billing period, which is the wrong shape for a product sold in bursts. An AI assistant that advertises "resets every 5 hours", or a plan that caps spend at $50 a day, cannot express that as a monthly limit. Entitlement grants turn an entitlement into a quota per window instead, on a clock of your choosing. Flexprice opens a window when usage starts, tracks consumption against the quota, fires a webhook when the quota is exhausted, and bills usage beyond it as overage on the invoice.

**Benefits:**

- **Rolling limits:** quotas measured in hours, days, or weeks instead of the billing period
- **Parallel limits:** stack independent windows on one feature, such as an hourly limit and a weekly limit
- **Amount-based quotas:** cap spend in currency, priced through your existing billing pipeline
- **Exhaustion webhooks:** `entitlement.grant.exhausted` fires when a window's quota is used up
- **Overage billing:** usage beyond the quota lands on the arrears invoice automatically

## Concepts

| Term | Meaning |
|------|---------|
| **Allowance** | The rule you configure on an entitlement: how much, how often, and how it stacks. |
| **Window** | One concrete stretch of time instantiated from that rule, with its own quota and its own usage. A grant that resets hourly produces one window per hour of activity. |
| **Value type** | What the quota counts: quantity (meter units) or amount (currency, priced through your existing meter prices). |
| **Stacking** | How several allowances on the same feature combine: additive merges them into one pool, parallel keeps each on its own clock. |

## Setting Up a Grant

A grant is an entitlement with a recurring value, so it is configured wherever entitlements are: on a plan, or on an addon. The feature must be metered.

<Steps>
  <Step title="Open the plan's entitlements">
    Go to **Product Catalog** and open the plan, then the **Entitlements** section. Click **Add**.
  </Step>

  <Step title="Pick the feature and set the value">
    Select the metered feature. Choose a **Value Type** of **Quantity** to count meter units or **Amount** to cap spend in currency, then enter the **Value**, or switch on **Unlimited** for no ceiling.

    <Frame>
      ![Configure an entitlement grant](/images/docs/product-catalogue/features/entitlement-grants/add-entitlement.png)
    </Frame>
  </Step>

  <Step title="Choose how often it resets">
    **Usage resets** sets the cadence: **Hourly**, **Daily**, **Weekly**, or **Every billing period**. This is what makes the allowance recurring rather than a single limit for the cycle.
  </Step>

  <Step title="Set the advanced options if you need them">
    Under **Advanced**, **Window starts** decides where each window begins, and **Stacking** decides how this allowance combines with others on the same feature. Both are explained below.
  </Step>

  <Step title="Save">
    Click **Add**, then save the plan. The allowance applies to every customer on the plan.
  </Step>
</Steps>

### Settings and Their API Fields

The dashboard and the API name these settings differently. Everything you set in the drawer is a field on the [create entitlement](/api-reference/entitlements/create-entitlement) and [update entitlement](/api-reference/entitlements/update-entitlement) endpoints.

| Dashboard | API field | Values |
|---|---|---|
| Value Type | `grant_measure` | `quantity` or `amount` |
| Value | `grant_quota` | A decimal string |
| Unlimited | `grant_unlimited` | `true` for no ceiling. Mutually exclusive with `grant_quota`. |
| Usage resets | `grant_duration_unit` and `grant_duration_value` | `hour`, `day`, `week`, or `subscription_period` |
| Window starts | `grant_allocation_behavior` | `first_usage` or `unit_start` |
| Stacking | `aggregation_mode` | `additive` or `parallel` |

A fixed-duration window must be at least one hour long.

<Warning>
Allowances are validated when you save:

- The feature must be metered. Meters with `MAX` aggregation or bucketed aggregation are not supported.
- All allowances on one feature must share the same value type and the same stacking. Additive allowances must also share the same cadence.
- Amount allowances require flat per-unit pricing on the meter. Tiered prices are rejected.
- **Unlimited** is only available with a cadence of **Every billing period**. A recurring window needs a finite value.
</Warning>

### Unlimited Allowances

Switch on **Unlimited** to give a customer an uncapped allowance for the billing cycle. The entitlement still reports usage and still appears in the ledger, but no quota is enforced, nothing is ever exhausted, and no overage is billed.

This is how you remove a ceiling from a metered entitlement. Use it in place of the legacy `usage_limit` and `usage_reset_period` fields, which metered entitlements are moving off.

### Where a Window Starts

**Window starts** decides how each new window is anchored:

- **On first use** (`first_usage`) starts the window at the customer's first event past the covered range. An event at 2:07 opens a window that runs 2:07 to 7:07 for a five-hour allowance, so each customer's windows follow their own activity.
- **Calendar boundary** (`unit_start`) rounds the start down to the hour, day or week. That same event at 2:07 opens a window running 2:00 to 7:00. Use it when every customer should see the allowance reset on the clock.

The setting applies only to fixed cadences. An allowance that resets every billing period always runs with the subscription cycle.

### Changing an Allowance Mid-Cycle

Editing an entitlement that customers are already using does not always take effect at once, because a window that is open has usage measured against it already.

| Change | When it takes effect |
|---|---|
| Raising the value | Immediately, on the open window |
| Lowering the value, still above what has been used | Immediately, on the open window |
| Lowering the value below what has been used | When the current window ends |
| Changing the cadence, value type or stacking | When the current window ends |

Usage already recorded in the open window still counts. A customer on a 1,000 unit hourly allowance who has spent 400 and is moved to 600 has 200 left, not 600. The dashboard tells you which case you are in before you save.

<Warning>
This applies to an entitlement edited on a **subscription**. Editing the **plan's** entitlement changes the rule for future windows and for new subscribers; it does not re-cut windows already open on existing subscriptions.
</Warning>

## How Grant Windows Work

Windows are usage-anchored. Flexprice does not open a window on a fixed schedule; it opens one when usage arrives:

1. The first usage event past the covered range opens a window, anchored according to **Window starts**.
2. The window runs for the configured cadence.
3. When the window ends, nothing happens until the next usage event. Idle periods open no windows, so an inactive customer accumulates nothing.
4. Windows never straddle billing cycles. A window that would end within an hour of the cycle boundary stretches to the boundary instead of leaving a short stub.

A window is **active** while usage is below its quota and **exhausted** once usage reaches it. Expiry is not a state: a window is closed when its end has passed, regardless of how much was used.

<Note>
Usage is measured against the window's own time range, not accumulated as events arrive. An event that reaches Flexprice late counts against the window its timestamp falls in, so a backfill can change what a window that has already closed reports, and can exhaust it after the fact.
</Note>

## Viewing Usage and Windows

A customer's **Entitlements** table lists what they hold and how much of it they have spent.

<Frame>
  ![Entitlements on a customer, with values, stacking and usage](/images/docs/product-catalogue/features/entitlement-grants/entitlements-table.png)
</Frame>

| Column | Shows |
|---|---|
| Feature | The metered feature the allowance is on |
| Source | Where the allowance comes from: the plan, an addon, or the subscription itself when it was edited there |
| Value | The allowance and its cadence, such as `100,000 / hour` or `50 / billing period`, or `Unlimited` |
| Mode | `Additive` or `Parallel` |
| Measure | `Quantity` or `Amount` |
| Usage | Consumption against the live allowance |

A parallel feature gets one row per budget, since no single pair of numbers describes them together. In the example above, Image Generations carries 500 per day from the Pro plan and 5,000 per week from the Token Booster addon, each metering the same usage on its own clock.

Selecting a row opens **Grants**, the ledger of windows behind that number.

<Frame>
  ![The grants ledger for a feature, one row per window](/images/docs/product-catalogue/features/entitlement-grants/grants-ledger.png)
</Frame>

| Status | Meaning |
|---|---|
| Active | Open now, with quota left |
| Exhausted | Quota reached. Hover the pill for the moment it was crossed. |
| Closed | The window ended without the quota being reached |
| Scheduled | The window starts later. You see this between attaching an addon with an effective date in the future and that date arriving, or on a subscription whose start date is still ahead. A recurring allowance never opens its next window ahead of time, and a change scheduled for period end does not produce one either. |

### Reading the Same Thing Over the API

[Get customer usage summary](/api-reference/customers/get-customer-usage-summary) returns the grant config for each feature plus a `grant_state.allowances` array, one entry per window:

| Field | Description |
|-------|-------------|
| `quota`, `usage` | The window's ceiling and what has been spent against it |
| `remaining` | What is left. Absent on an unlimited window, where there is no ceiling to measure against. |
| `valid_from`, `valid_to` | The window boundaries |
| `status` | `active` or `exhausted` |
| `is_active` | Whether the window is open right now, decided by the server's clock. A window whose `valid_from` is still ahead reports `false`: it is scheduled, not closed. |
| `quota_crossed_at` | When usage first reached the quota. Absent while the window still has room, and on an unlimited window. Overage is billed from this timestamp, so this answers "when did it run out", which `valid_to` does not. |
| `unlimited` | `true` when the window has no ceiling |

Only the current billing period is returned, capped at the three most recent windows per entitlement.

A **parallel** feature also carries a `buckets` array, one entry per budget with its own quota, cadence and value type. Read those instead of `total_limit` when `buckets` is present.

Allowances are listed per subscription rather than merged, so a customer holding one feature on two subscriptions sees two sets of windows. Tell them apart with `entitlement_id`. Inherited subscriptions carry none of their own; their usage belongs to the [parent](/docs/subscriptions/customer-hierarchy).

## Stacking

When a customer holds more than one allowance on the same feature, such as a plan entitlement plus an addon entitlement, **Stacking** decides how they combine.

### Additive

All allowances merge into **one** window whose quota is their sum. Use this when an addon should top up the base allowance.

**Example**: The Pro plan grants 100K tokens per day. A booster addon grants another 50K per day. The customer gets one daily window with a 150K quota.

### Parallel

Each allowance opens its **own** window on its own clock. All of them meter the same usage stream. A request is within limits only while every applicable window has quota left; exhausting any one window puts the feature into overage for the remainder of that window.

**Example**: 1M tokens per 5 hours *and* 5M tokens per week, as two parallel allowances. Heavy use exhausts the 5-hour window first; sustained use over days exhausts the weekly window even though no single 5-hour burst did.

## Use Cases

### Rolling Rate Limits for an AI Product

Cap token consumption in a rolling window that has nothing to do with the monthly invoice, the pattern used by AI assistants that advertise "resets every 5 hours".

| Setting | Value |
|---|---|
| Value Type | Quantity |
| Value | 1,000,000 |
| Usage resets | Hourly |
| Window starts | Calendar boundary |
| Stacking | Parallel |

Add a second parallel allowance that resets weekly to layer a sustained ceiling on top of the burst limit.

### Daily Spend Cap

Cap what a customer's usage *costs* rather than how many units they consume. An amount allowance prices usage through your existing meter prices, so a mid-window price change is respected.

| Setting | Value |
|---|---|
| Value Type | Amount |
| Value | 50 |
| Usage resets | Daily |
| Stacking | Additive |

The customer gets $50 of compute per day. Alert on exhaustion, or let usage continue and bill the excess as overage.

### Plan Plus Booster Addon

Sell top-ups without new plumbing. The plan carries an allowance; the addon carries another on the same feature with **Additive** stacking. Buying the addon raises the shared window's quota by the addon's amount. With **Parallel** instead, the addon grants a separate window, useful when its allowance runs on its own clock.

### Soft Limits With Billed Overage

Grants implement soft limits: usage is never blocked. When a window's quota is crossed, usage recorded after the crossing is billed as overage on the subscription's arrears invoice. Quantity overage is priced as billable units; amount overage lands directly as a charge. With parallel windows, overlapping overage periods are merged so a unit of usage is never billed twice.

<Note>
Overage folding skips line items with tiered prices, commitments, or true-up. Those price against the full cycle, so grant overage on them falls back to the standard billing calculation.
</Note>

## Exhaustion Alerts

Usage is measured shortly after events arrive, within roughly five minutes. When a window's usage reaches its quota the window turns exhausted and a webhook fires, once per window. There is no recovery event: a fresh window with a fresh quota simply opens when the next one starts.

### Webhook Fields

| Field | Description |
|-------|-------------|
| `alert_type` | Always `entitlement_grant_exhausted` |
| `alert_status` | `in_alarm` when the quota is exhausted |
| `usage_ratio` | `usage / quota` at evaluation time, `1` or more when exhausted |
| `triggered_at` | When the exhaustion was detected |
| `subscription` | The owning subscription, without line items or plan expansions |
| `customer` | The customer the grant belongs to |
| `entitlement` | The allowance the window was instantiated from |
| `entitlement_grant` | The exhausted window, including `quota`, `usage`, and the window boundaries |
